Google Cloud published a detailed guide yesterday for **Mantis**, its open-source harness for finding, reproducing, triaging and fixing software vulnerabilities.

The interesting part isn't that an LLM can find bugs. Google says that is increasingly possible. The hard part is determining whether a suspected vulnerability is **actually exploitable**, reproducing it safely, and verifying that the proposed fix works. Mantis addresses this with a multi-agent workflow involving strategy, research, critic/review agents and sandboxed vulnerability reproduction. ([Google Cloud](https://cloud.google.com/blog/products/identity-security/getting-started-with-the-mantis-harness-to-find-and-fix-bugs?utm_source=chatgpt.com "Getting started with the Mantis harness to find and fix bugs | Google Cloud Blog"))

One particularly good systems optimization is its **hierarchical security summary tree**:

```text
Repository
   │
   ├── Directory summaries
   │      │
   │      └── File summaries
   │
   ↓
Strategist
   ↓
Targeted research agents
   ↓
Reproduction sandbox
   ↓
Patch
   ↓
Verification
```

Google reports that this reduces token overhead by **more than 85%** while retaining important repository structure. ([Google Cloud](https://cloud.google.com/blog/products/identity-security/getting-started-with-the-mantis-harness-to-find-and-fix-bugs?utm_source=chatgpt.com "Getting started with the Mantis harness to find and fix bugs | Google Cloud Blog"))

### Why it matters to you

This is probably today's **highest-learning-value item**.

Notice what Google isn't doing:

```text
Repository
   ↓
LLM reads everything
   ↓
"Find vulnerabilities"
```

Instead:

```text
Architecture context
       ↓
Targeted retrieval
       ↓
Specialized investigation
       ↓
Deterministic reproduction
       ↓
Patch
       ↓
Verification
```

That architecture is extremely transferable to your own projects.

For example, your future **PKM/architecture reviewer** could work exactly this way:

- strategist → identify suspicious/incomplete areas
    
- researcher → inspect relevant notes
    
- critic → challenge conclusions
    
- verifier → check links/metadata/programmatic invariants
    
- fixer → propose changes
    
- regression evaluator → verify nothing broke
    

The 85% context reduction is also a useful lesson for your RAG work:

> **Good context engineering isn't "retrieve more." It's preserving the right structure while retrieving less.**

Meta published a fascinating engineering paper yesterday describing an **Organizational Second Brain**: an AI agent designed to preserve specialist knowledge and make it reusable across an organization.

The system deliberately separates:

1. **what the agent knows**
    
2. **how the agent reasons**
    

The knowledge layer is structured and auditable. Expert corrections are fed through a self-improvement loop that produces **verified, regression-tested knowledge updates without retraining the underlying model**. ([Engineering at Meta](https://engineering.fb.com/2026/09/02/ml-applications/organizational-second-brain-ai-learns-from-experts/?utm_source=chatgpt.com "An Organizational Second Brain: Building an AI That Learns From Experts - Engineering at Meta"))

Conceptually:

```text
             Expert
               │
          correction
               ↓
       Knowledge update
               ↓
        Verification
               ↓
      Regression tests
               ↓
        Knowledge base
               ↓
             Agent
```

### Why it matters to you

This is the most directly relevant story today for your **Akashic Records / PKM work**.

It validates a very important architectural choice:

> **Don't put personal or organizational knowledge into model weights if you can represent it as an external, auditable knowledge system.**

That gives you:

- updateability
    
- provenance
    
- versioning
    
- rollback
    
- testing
    
- explainability
    
- model independence
    

And there's a particularly interesting distinction:

```text
Model
 = reasoning capability

Knowledge system
 = accumulated expertise
```

That means a better model doesn't require rebuilding the organization's institutional memory.

### The experiment I'd steal

Your PKM already has metadata, grades, links, ADRs and structured notes.

Build:

```text
Expert correction
       ↓
Candidate note update
       ↓
Automated checks
       ↓
Regression evaluation
       ↓
Versioned knowledge
       ↓
Agent uses updated knowledge
```

Then track whether the correction actually improves future agent answers.

That would turn your PKM from a **repository of notes** into a **continuously evaluated knowledge system**.

That's a much more interesting project.

GitHub made **Copilot content exclusions generally available in the Copilot app and CLI on September 2**.

Enterprise, organization and repository administrators can now define files/directories that Copilot must not use as context, and those exclusions are respected during **agentic workflows**, not merely autocomplete. ([The GitHub Blog](https://github.blog/changelog/2026-09-02-content-exclusions-generally-available-in-copilot-app-and-cli/?utm_source=chatgpt.com "Content exclusions generally available in Copilot app and CLI - GitHub Changelog"))

This matters because GitHub is simultaneously moving toward a unified Copilot experience where the web interface and cloud agent converge into the same agent-session model. GitHub says the unified experience is planned no earlier than September 28. ([The GitHub Blog](https://github.blog/changelog/2026-08-28-upcoming-changes-to-github-copilot-policies-and-billing/?utm_source=chatgpt.com "Upcoming changes to GitHub Copilot policies and billing - GitHub Changelog"))

### Why it matters to you

This is a subtle but important evolution:

```text
Old AI security

"What can the model generate?"


New AI security

"What information can the model see?"
+
"What actions can it perform?"
```

Those are separate permissions.

A coding agent might have permission to modify:

```text
src/
tests/
```

while being forbidden from seeing:

```text
credentials/
production-config/
customer-data/
```

That's **context-level authorization**.

And it's increasingly important because agentic workflows ingest much more repository context than autocomplete ever did.

### Why this matters for your projects

When you build an agent over your PKM or GitHub repositories, don't make access binary:

```text
agent → entire repository
```

Instead think:

```text
Agent
 ├── allowed knowledge
 ├── excluded knowledge
 ├── allowed tools
 ├── allowed operations
 └── allowed environments
```

That's a very good architecture pattern for your future **Career Architect / PKM Curator / Project Reviewer agents**.

Amazon Web Services published a new **Agentic Security** framework on September 2, developed with the SANS Institute.

AWS argues that autonomous agents fundamentally change the security posture because agents can authenticate on behalf of users, execute multi-step workflows and make infrastructure decisions without waiting for human approval. ([Amazon Web Services](https://aws.amazon.com/blogs/security/agentic-security-detection-and-response-at-machine-speed/?utm_source=chatgpt.com "Agentic security: Detection and response at machine speed | AWS Security Blog"))

The proposed security approach emphasizes:

- agent identity
    
- least privilege
    
- continuous monitoring
    
- runtime detection
    
- behavioral analysis
    
- rapid containment
    
- incident response designed for autonomous workloads
    

### Why it matters to you

We've covered individual pieces of this in previous briefings.

What's useful here is seeing them converge into a **security lifecycle**:

```text
              Agent
                │
        ┌───────┴───────┐
        ↓               ↓
      Identity        Tools
        │               │
        └───────┬───────┘
                ↓
             Execute
                ↓
            Observe
                ↓
             Detect
                ↓
            Contain
                ↓
            Recover
```

The key architectural shift is:

> **Security can't end at authorization.**

An agent may be authorized to perform an action and still behave anomalously.

That means you need both:

**preventive controls**

and

**behavioral detection**.

### Why this is relevant to your career

For senior Data Engineering/AI architecture, this becomes especially important when agents can touch:

- databases
    
- data warehouses
    
- cloud APIs
    
- pipelines
    
- production infrastructure
    
- customer data
    

I'd start thinking of an agent like a **new workload identity**, not a fancy API client.

That mental model will serve you well.

![Image](https://images.openai.com/static-rsc-4/P5xxYs-bacQuSP_CKN6PLEhz8GniyZTvTFTfwzxP2wwSynTZfQZMOpUqi5ZdJm-DyugVRAFzfvA04JpP6HisIUUvs2Ekn8cy7itgP3XH2z6e4_ehQVfZ9hVBG2g4Nhmt_51s6K39yyVkyUDtKD8X1xJCpWf_7AMUzk3N9FpzEjEEmKvHtyV6U3ITSkmHY6x9?purpose=fullsize)

![Image](https://images.openai.com/static-rsc-4/nVbFEIgix0J1mEdNpV6ktgeluew3gdH3tPow4kLF7MYhXqwM3vVO7yPgBDKjM2mnenmYXsdNA97QcxJGDppbINEM7zy2zw6glj-2HWViJZ5ln_Do2ELqC0Guqas7_APL3zaXDjilVu-8mk7cHaekVsTmLQZvmBnHNsIjw9F4hFz3MYxoA8fvnRvUbP-ZYYox?purpose=fullsize)

ClickHouse has published a detailed architecture for using **chDB**, an embedded ClickHouse engine, as an agent's local data layer.

The argument is straightforward: an agent may make **5–20 sequential tool calls** during one task. If every data lookup crosses a network boundary, latency compounds and transient failures trigger retries and additional model calls. ([ClickHouse](https://clickhouse.com/blog/chdb-agents-local-data-engine?utm_source=chatgpt.com "chDB as the Agent's Local Data Engine | ClickHouse"))

Their proposed architecture puts the analytical engine directly inside the agent process:

```text
                 Agent
                   │
              ┌────┴────┐
              │  chDB   │
              │ locally │
              └────┬────┘
                   │
            local working set
                   │
          ┌────────┴────────┐
          ↓                 ↓
       memory            cached data
          │
          ↓
      reasoning
```

ClickHouse describes three uses:

- local agent memory
    
- a local federation/query hub
    
- reduced latency and token waste from repeated remote calls ([ClickHouse](https://clickhouse.com/blog/chdb-agents-local-data-engine?utm_source=chatgpt.com "chDB as the Agent's Local Data Engine | ClickHouse"))
    

### Why it matters to you

This connects directly to your **local-first** interests.

The traditional architecture is:

```text
Agent → API → warehouse → API → agent
```

But for a bounded working set:

```text
Agent
  ↓
local analytical engine
  ↓
fast filtering/joining/aggregation
  ↓
small result
  ↓
LLM
```

is often much cleaner.

And this isn't limited to ClickHouse.

The general architecture applies to:

- DuckDB
    
- chDB
    
- SQLite
    
- PGlite
    
- Arrow
    
- local Parquet
    
- embedded vector indexes
    

The broader principle is:

> **Don't send the agent to the data for every tiny operation; sometimes bring the relevant data closer to the agent.**

That's particularly interesting for your PKM.

Imagine the agent locally querying:

```text
notes
links
grades
projects
ADRs
daily notes
```

using SQL before asking the LLM to reason over the result.

That's arguably a better architecture than stuffing hundreds of Markdown files into a prompt.

[ClickHouse — chDB as the Agent's Local Data Engine](https://clickhouse.com/blog/chdb-agents-local-data-engine?utm_source=chatgpt.com)

## Today's bigger signal

The five stories point toward a common architecture:

```text
                         Agent
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
           Context       Identity      Tools
              │            │            │
          PKM / DB       Policy        MCP
              │            │            │
              └────────────┼────────────┘
                           ↓
                    Local / Remote
                    execution layer
                           │
                    Deterministic
                     verification
                           │

                    ↓             ↓
                 Observe       Evaluate
                    │             │
                    └──────┬──────┘
                           ↓
```

The interesting frontier is increasingly **not model intelligence**.

It's the machinery around the model:

**context selection, durable knowledge, identity, permissions, local data processing, verification, evaluation and feedback.**

And there's a particularly strong takeaway for your own work:

> **Your PKM could become an agent operating system rather than merely a knowledge repository.**

The pieces you're interested in—structured metadata, knowledge graphs, quality scores, embeddings, project context, ADRs, local-first storage and specialized agents—are starting to look less like separate features and more like components of the same architecture.
