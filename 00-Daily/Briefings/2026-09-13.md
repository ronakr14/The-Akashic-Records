Databricks expanded **Genie Agents** on September 10. Each agent can now use up to **50 tables, views, or metric views**, up from 30, while its conversation capacity increased from 10,000 to 200,000 conversations. Databricks also provides a managed **Genie Agent MCP server**, allowing external agents and tools such as coding assistants to query a curated Genie Agent using natural language while Unity Catalog permissions are enforced on every request. The architectural bit I care about is the separation:

```text
External Agent
     │
     ▼
   MCP
     │
     ▼
Genie Agent
     │
     ├── semantic/context layer
     ├── trusted assets
     ├── example SQL
     └── instructions
     │
     ▼
Unity Catalog
     │
     ▼
Lakehouse
```

Databricks explicitly recommends Genie Agents when an agent needs to query structured Unity Catalog data, while deterministic UC functions can be used where reproducibility matters. ([Databricks Documentation](https://docs.databricks.com/aws/en/agents/custom-agents/structured-retrieval-tools?utm_source=chatgpt.com "Connect agents to structured data | Databricks on AWS"))

### Why it matters to you

This is **very close to the architecture you should be studying** for your move from data engineering toward AI architecture.

The important idea is that you don't let an LLM loose on the entire warehouse.

Instead:

**curated context → semantic boundary → governed tool → deterministic execution**

That's a much stronger pattern than generic text-to-SQL.

It also gives you a concrete direction for the **Akashic Records**:

> Markdown/metadata → curated semantic layer → MCP → specialized agents.

And for your Lakehouse Copilot:

> workload metadata → optimizer context → controlled tools → actions.

**Practical experiment:** expose a small DuckDB/Postgres dataset through an MCP server and deliberately restrict the agent to a curated schema. Measure how much accuracy improves when the context boundary is narrower.

A fascinating engineering post from Meta describes **ZGateway**, a new proxy tier placed in front of ZippyDB. More interestingly, Meta says many of the system's existing operational heuristics—load shedding, balancing, failover, cache bounds and batch windows—already behave like control loops. ### Why it matters to you

This is a much more interesting direction than "AI writes code."

The emerging architecture is:

```text
Production system
      │
      ▼
Telemetry / metrics
      │
      ▼
State estimation
      │
      ▼
Agent / optimizer
      │
      ▼
Candidate action
      │
      ▼
Policy / safety boundary
      │
      ▼
Production change
      │
      └──────────────► feedback
```

That's essentially **closed-loop engineering**.

And it maps directly onto your Lakehouse Optimization project.

Your original concept is already heading here:

**observe → diagnose → recommend → optimize**

The next evolution is:

**observe → hypothesize → experiment → measure → decide → apply → verify**

That's far more compelling.

### Practical experiment

Build a toy optimizer around a DuckDB workload:

1. collect query runtime/scan/cardinality metrics,
    
2. generate optimization hypotheses,
    
3. test candidate indexes/partitioning/query rewrites,
    
4. benchmark them,
    
5. retain only statistically useful changes.
    

You've now built a miniature version of the same **agentic control-loop architecture**.

Kubernetes 1.37's current release series is introducing several substantial scheduling changes.

The most relevant for AI/data infrastructure is **Dynamic Resource Allocation (DRA)**: DRA Extended Resource support has reached GA, while fractional resource allocation and scheduler improvements are progressing through beta/alpha. Kubernetes reports that a new pre-queueing mechanism can reduce an expensive requeue path from roughly **O(N²) to O(1)** in the affected scheduling scenario, with early benchmarks showing roughly 2× scheduling throughput. ([Kubernetes](https://kubernetes.io/blog/2026/09/03/kubernetes-v1-37-dra-updates/?utm_source=chatgpt.com "Kubernetes v1.37: DRA Updates | Kubernetes"))

Kubernetes is also introducing **workload-aware scheduling** improvements specifically in response to AI/ML and complex batch workloads, while node lifecycle conditions are being added as a common API for expressing node state. ([Kubernetes](https://kubernetes.io/blog/?utm_source=chatgpt.com "Kubernetes Blog | Kubernetes"))

### Why it matters to you

This is where your **data engineering → architecture** progression becomes relevant.

You don't need to become a Kubernetes operator.

But you should understand why modern platforms increasingly need to schedule based on:

- GPU/accelerator availability
    
- fractional resources
    
- workload groups
    
- priority
    
- locality
    
- capacity
    
- failure domains
    
- scaling behavior
    

The architecture question becomes:

> **Where should this computation run, and what resources should it consume?**

That's relevant to Spark, Databricks, Ray, model serving, batch ETL and agent infrastructure alike.

**What I'd learn:** DRA + workload-aware scheduling, not Kubernetes YAML trivia.

```text
Models
  ↓

  ↓

  ↓
Data centers
  ↓

  ↓
```

That means architecture discussions increasingly include:

- utilization

- accelerator selection
    
- cooling
    
- network topology
    
- workload placement
    
- cost per inference
