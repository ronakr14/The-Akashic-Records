## 1. Anthropic turns Claude Projects into a **multi-agent workspace with a coordinator**

Anthropic has relaunched **Claude Code Projects** as a coordinated multi-agent workspace. A project can now contain multiple parallel agent threads, shared memory and a common file library; a central coordinator can divide work among threads, while each thread can operate on its own repository branch. The feature is currently rolling out in beta. ([The Verge](https://www.theverge.com/ai-artificial-intelligence/997134/anthropic-claude-code-projects "Claude Code relaunches Projects to manage multiple AI agents in the cloud"))

The interesting architecture is:

```text
                         Project
                            │
                     ┌──────▼──────┐
                     │ Coordinator │
                     └──────┬──────┘
                            │
             ┌──────────────┼──────────────┐
             ↓              ↓              ↓
         Agent A          Agent B        Agent C
         Research         Coding         Testing
             │              │              │
          Branch A        Branch B       Branch C
             └──────────────┼──────────────┘
                            ↓
                      Shared memory
                            ↓
                       Integration
```

The agents can also subdivide their work further using subagents, loops and workflows. ([The Verge](https://www.theverge.com/ai-artificial-intelligence/997134/anthropic-claude-code-projects "Claude Code relaunches Projects to manage multiple AI agents in the cloud"))

### Why it matters to you

This is highly relevant to your **Akashic Agent Workspace** idea.

The architecture is moving from:

> one agent → one task

toward:

> **coordinator → specialized agents → shared state → integration**

That's a fundamentally different systems problem.

You should start thinking about:

- task decomposition
    
- agent specialization
    
- shared memory
    
- branch isolation
    
- conflict resolution
    
- dependency management
    
- failure recovery
    
- result aggregation

### Practical experiment

Your Akashic agents could become:

```text
Career Architect
      │
      ├── Data Engineering Analyst
      ├── AI/LLM Researcher
      ├── PKM Curator
      ├── Project Reviewer
      └── Interview Coach
```

Give each agent a **narrow mandate and separate workspace**, then add a coordinator responsible for deciding which agent gets which task.

That is much closer to a real multi-agent architecture than having five prompts sitting in a folder.

**Source:** [The Verge — Claude Code Projects relaunch](https://www.theverge.com/ai-artificial-intelligence/997134/anthropic-claude-code-projects)

## 2. GitHub's **HydraFusion** demonstrates that model selection is becoming runtime orchestration

GitHub's **Project HydraFusion**, currently a research preview in Copilot, goes beyond simple automatic model selection. It creates an execution plan and can choose among models from multiple providers to **draft, critique, revise, or cascade to stronger models** when necessary. GitHub reports that selective workflows matched or exceeded the evaluated Opus 5 baseline in offline evaluations while reducing estimated workflow cost. ([The GitHub Blog](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/ "Project HydraFusion: Frontier quality via multi-model orchestration - The GitHub Blog"))

Conceptually:

```text
                  Coding Task
                      │
                      ▼
                Task Classifier
                      │
                Execution Plan
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
      Model A       Model B       Model C
       draft         critique      verify
        │             │             │
        └─────────────┼─────────────┘
                      ↓
                 Final result
```

GitHub's weekly release notes say HydraFusion is also experimenting with **semantic routing between local, cloud and compound models**. ([The GitHub Blog](https://github.blog/changelog/2026-09-10-github-copilot-weekly-releases-september-7/ "GitHub Copilot weekly releases — September 7 - GitHub Changelog"))

### Why it matters to you

This is one of the most important architectural trends for your **Lakehouse Copilot**.

Model selection shouldn't be:

> "GPT vs Claude?"

It should become:

> **"What is the cheapest execution strategy that satisfies the quality requirement?"**

That's an optimization problem.

You can model it as:

```text
minimize:
    inference_cost + latency + failure_cost

subject to:
    quality >= threshold
```

This fits naturally with your existing interest in **cost optimization**.

### Practical experiment

Build a tiny router:

```text
Simple SQL question
      → small/local model

Complex query optimization
      → stronger model

Architecture design
      → strongest reasoning model

Verification
      → independent model
```

Log:

- model selected
    
- latency
    
- tokens
    
- cost
    
- quality score
    
- retries
    
- final outcome

You'd have the skeleton of an **AI workload optimizer**.

**Source:** [GitHub — Project HydraFusion](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/)

## 3. Z.ai describes an **AI agent helping build its own inference infrastructure**

Z.ai published an unusually interesting engineering post on September 17 describing how it built the production inference system for **GLM-5.3-Flash** across a cluster of more than **100,000 Chinese-made AI accelerators**.

Z.ai says the system had to deal with limited accelerator memory and bandwidth, a 1M-token context window, multimodal requests and an immature software ecosystem. More unusually, it says much of the infrastructure work was performed with help from an **"Infra Agent" powered by GLM-5.3**. ([Z.ai](https://z.ai/blog/glm-built-its-inference-infrastructure "Toward Recursive Self-Improvement: How GLM Built Its Own Inference Infrastructure"))

Z.ai also reports that GLM-5.3-Flash uses **320B total parameters but only 18B active parameters**, with a hybrid sparse/linear attention architecture aimed at inference efficiency. ([AutoClaw](https://autoclaw.z.ai/blog/model/glm-5.3-flash/ "GLM-5.3-Flash: More Intelligence with Less Compute | AutoClaw Blog"))

The interesting feedback loop is:

```text
             Model
               ↓
         Infrastructure
               ↓
            Telemetry
               ↓
          Infra Agent
               ↓
      Optimization proposal
               ↓
          Benchmark/test
               ↓
        Production system
               └──────────→ feedback
```

### Why it matters to you

This is a fascinating example of **AI improving the infrastructure used to run AI**.

It connects directly to the idea we've discussed around your Lakehouse Optimizer:

**observe → reason → optimize → test → deploy → observe again**

The important part is that the agent doesn't simply generate infrastructure code.

It operates inside an engineering feedback loop with measurable system behavior.

That's the architecture pattern worth stealing.

### Practical experiment

You don't need 100,000 accelerators.

Take a local workload:

```text
DuckDB query
   ↓
benchmark
   ↓
agent proposes optimization
   ↓
execute candidate
   ↓
compare runtime/memory
   ↓
accept/reject
```

Then make the optimizer **prove its recommendation with a benchmark** before allowing it to become the new configuration.

That gives you a miniature self-optimizing system.

**Source:** [Z.ai — How GLM Built Its Inference Infrastructure](https://z.ai/blog/glm-built-its-inference-infrastructure)

## 4. Databricks is making **Agent Skills** portable across coding assistants

Databricks updated its documentation on **September 17** for **Agent Skills for AI coding assistants**. The skills are task-specific Markdown instruction packages that coding agents such as Claude and GitHub Copilot can automatically discover and load when working with Databricks resources. They use the open **Agent Skills standard** and can be installed through the Databricks CLI `aitools` command. ([Databricks Documentation](https://docs.databricks.com/gcp/en/agent-skills/ "Agent skills for AI coding assistants | Databricks on Google Cloud"))

The structure is deliberately simple:

```text
skill/
├── SKILL.md
├── instructions
├── examples
└── supporting resources
```

with frontmatter describing when the skill should be activated.

### Why it matters to you

This is **extremely relevant to your PKM architecture**.

You've been building structured notes with metadata like:

- domain
    
- subdomain
    
- note type
    
- level
    
- status
    
- confidence
    
- completeness

Agent Skills introduces a similar concept from the other direction:

> **knowledge packaged specifically for machine execution.**

That's an important distinction.

A normal documentation page says:

> "Here's everything about Databricks."

A skill says:

> **"When you're doing X, follow this exact workflow and use these resources."**

That's much more useful to agents.

### A direction I'd seriously consider for Akashic

Add an `agent-skills/` layer:

```text
agent-skills/
├── data-engineering/
│   ├── spark-optimization/
│   ├── delta-design/
│   └── sql-review/
├── architecture/
│   ├── adr-review/
│   └── system-design/
└── career/
    ├── interview-review/
    └── skill-gap-analysis/
```

Your PKM then becomes more than a knowledge repository.

It becomes:

> **a machine-readable operating system for your agents.**

That is a genuinely interesting direction for a personal knowledge system.

## 5. Agent isolation is showing a new class of **supply-chain security problem**

Security researchers reported this week that multiple AI coding agents can be affected by an isolation weakness involving **shared infrastructure such as package caches**. The core concern is that an agent may appear isolated at the process or workspace level while still interacting with shared host-level resources. ([InfoWorld](https://www.infoworld.com/article/4223350/your-ai-agents-are-isolated-your-infrastructure-isnt.html "Your AI agents are isolated. Your infrastructure isn’t"))

Separate reporting this week described a related **"GitSpawn"** vulnerability affecting several AI coding agents through Git configuration behavior, with some affected products reportedly still awaiting patches. Because these reports are still developing, the exact impact varies by agent/version and should be checked against vendor advisories before treating any one exploit path as confirmed for a particular product. ([shattered.io](https://shattered.io/gitspawn-ai-coding-agent-vulnerability-2026/ "GitSpawn Flaw Hits 7 AI Coding Agents, 4 Unpatched [2026]"))

The architectural issue is more important than any individual CVE:

```text
                 Agent
                   │
              Sandbox
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
     Files       Network     Process
       │           │           │
       └───────────┼───────────┘
                   ↓
             Shared Host
          / cache / socket /
             credentials
```

A sandbox isn't necessarily isolated if the agent can exploit **shared side channels or host resources**.

### Why it matters to you

This is directly relevant to the agent systems you're experimenting with.

The security principle I'd use is:

> **Isolation must be transitive.**

It's not enough to isolate the working directory.

You need to think about:

- filesystem mounts
    
- environment variables
    
- credentials
    
- package caches
    
- Git configuration
    
- sockets
    
- network access
    
- process namespaces
    
- container escape
    
- shared volumes
    
- secrets

This is the kind of detail that separates an agent prototype from an **enterprise-grade agent platform**.

### Practical experiment

Take one of your local coding agents and map its entire trust boundary:

```text
Agent
 ├── filesystem
 ├── environment
 ├── Git
 ├── network
 ├── package manager
 ├── credentials
 └── host services
```

For every item ask:

**Can the agent read it? Modify it? Persist through it? Reach the host through it?**

That's a very worthwhile security exercise.

**Sources:** [InfoWorld — Agent isolation and shared infrastructure risks](https://www.infoworld.com/article/4223350/your-ai-agents-are-isolated-your-infrastructure-isnt.html) · [GitSpawn vulnerability reporting](https://shattered.io/gitspawn-ai-coding-agent-vulnerability-2026/)
