## 1. GitHub rewrote the Copilot agent runtime in **800K+ lines of Rust — with agents doing much of the migration**

GitHub published a detailed engineering post on September 16 describing the migration of the runtime behind Copilot CLI, Copilot App and the Copilot SDK from TypeScript/Node.js to **more than 800,000 lines of production Rust**. The project ran incrementally while the existing system continued shipping, rather than using a risky big-bang rewrite. ([The GitHub Blog](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/ "Migrating the GitHub Copilot runtime to Rust, using Copilot - The GitHub Blog"))

The interesting part isn't "Rust is faster."

GitHub reports that, for its specific workload, the old runtime managed about **7.55 session lifecycles/sec**, compared with **57.45/sec out-of-process Rust and 120/sec in-process Rust**. In a separate 10-client test, aggregate CPU consumption dropped from about 312 seconds to about 110 seconds, while the measured private-memory increase dropped from roughly 1.38 GB to 126 MB for the in-process version. These are workload-specific internal benchmarks, not universal Rust-vs-TypeScript numbers. ([The GitHub Blog](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/ "Migrating the GitHub Copilot runtime to Rust, using Copilot - The GitHub Blog"))

The architectural transition is particularly interesting:

```text
Before

SDK
 ↓
JSON-RPC
 ↓
Node.js / TypeScript runtime
 ↓
Agent execution

After

SDK
 ↓
C ABI / native FFI
 ↓
Rust agent runtime
 ↓
Agent execution
```

The new runtime can be embedded in-process and exposed through FFI to **C#, TypeScript, Python, Rust, Go and Java**. ([The GitHub Blog](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/ "Migrating the GitHub Copilot runtime to Rust, using Copilot - The GitHub Blog"))

### Why it matters to you

This is a **systems-engineering masterclass disguised as a language migration**.

The real lesson is:

> AI agents don't eliminate software architecture. They change the economics of implementing it.

GitHub says the project became economically feasible because agents could perform huge amounts of repetitive porting work while engineers concentrated on architecture, review and validation. The migration still encountered dozens of correctness and lifecycle regressions, reinforcing that **AI-generated code needs strong test oracles and architectural oversight**. ([The GitHub Blog](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/ "Migrating the GitHub Copilot runtime to Rust, using Copilot - The GitHub Blog"))

For your career, this is valuable because it connects three areas you should increasingly combine:

**Python/software engineering + AI agents + systems architecture.**

### Practical experiment

Take a **small Python service** and have an agent create a Rust implementation while you define:

- API contract
    
- performance requirements
    
- test oracle
    
- compatibility criteria
    
- migration stages

Then compare:

**AI-generated implementation vs human architectural decisions.**

That's much closer to the future of engineering than "ask AI to write a CRUD API."

**Source:** [GitHub Engineering — Migrating the GitHub Copilot runtime to Rust](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/)

## 2. Databricks shows that **evaluation-first agents** are becoming production data engineering

Databricks published a September case study showing how Zepto uses Databricks and MLflow to operate an evaluation-first customer-support agent system. Databricks says the agents now handle **80%+ of support tickets**, reduced support costs by **65%**, and achieved payback in under a month. ([Databricks](https://www.databricks.com/blog/evaluation-first-ai-agents-how-zepto-scales-customer-support-databricks-and-mlflow "Evaluation-First AI Agents: How Zepto Scales Customer Support on Databricks and MLflow"))

The important architectural piece is not the headline numbers.

It's the lifecycle:

```text
                Agent
                  ↓
              Production
                  ↓
               Traces
                  ↓
             Evaluation
                  ↓
          Failure analysis
                  ↓
             Dataset
                  ↓
          Agent improvement
                  ↓
             Regression
                  ↓
             Production
```

MLflow provides tracing, evaluation, comparison and feedback mechanisms across agent versions, while the underlying data platform provides the governed data foundation.

### Why it matters to you

This is **directly aligned with where your skillset should go next**.

Your SDET experience isn't something you necessarily need to discard. You can turn it into an advantage:

> **Data engineering + AI evaluation + software testing = AI reliability engineering.**

For your Akashic project, don't just grade notes.

Start thinking about **evaluation datasets**:

```text
Question
   ↓
Expected evidence
   ↓
Agent response
   ↓
Evaluator
   ↓
Score
   ↓
Regression history
```

Then evaluate:

- factuality
    
- source coverage
    
- retrieval quality
    
- stale knowledge
    
- hallucination
    
- tool selection
    
- reasoning failures

That's a much stronger architecture than simply adding another vector database.

Save:

```text

```

Now you have the beginnings of an **AI evaluation dataset**.

## 3. Apache Iceberg Python 0.12 adds **REST Catalog view support**

The Apache Iceberg community released **PyIceberg 0.12.0 on September 3**, incorporating more than 470 pull requests from 58 contributors. One of the notable additions is support for **Iceberg views through the REST Catalog**, allowing views to be created, loaded, listed, registered and dropped through the catalog interface. ([Apache Iceberg](https://iceberg.apache.org/blog/apache-iceberg-python-0.12.0-release/ "Apache Iceberg Python 0.12.0 Release - Apache Iceberg™"))

That sounds minor until you consider the larger direction:

```text
                REST Catalog
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
        Spark      Python      Trino
          │          │          │
          └──────────┼──────────┘
                     ↓
               Iceberg Tables
                     ↓
                  Storage
```

The REST catalog is becoming an important interoperability boundary rather than just another metadata service.

### Why it matters to you

This is **senior-data-engineer territory**.

If you're aiming for architecture, you want to understand why organizations increasingly want:

**open storage + open table format + independent compute + standard catalog interface.**

That lets you reason about architectures without getting trapped inside a single vendor.

It also makes PyIceberg more interesting for your Python-heavy workflow.

Instead of:

> Python → proprietary warehouse API

you can increasingly think:

> Python → open catalog → Iceberg → whatever compute engine fits.

That's a much more portable architecture.

### Practical experiment

Build a tiny lakehouse locally:

```text
Python
  ↓
PyIceberg
  ↓
REST Catalog
  ↓
Iceberg
  ↓
Parquet
  ↓
DuckDB / Spark
```

Then deliberately access the same table from multiple engines.

Measure:

- metadata behavior
    
- schema evolution
    
- view support
    
- transaction semantics
    
- partition pruning
    
- interoperability

That is a **far better Iceberg exercise** than reading another "Iceberg vs Delta" comparison article.

**Source:** [Apache Iceberg — PyIceberg 0.12.0 release](https://iceberg.apache.org/blog/apache-iceberg-python-0.12.0-release/)

## 4. Neon is letting agents **create database branches and execute SQL through MCP**

Neon announced on September 1 that its PostgreSQL platform can be operated through **Grok Bot using Neon agent skills plus the Neon MCP Server**.

The agent can create Neon projects, create isolated database branches before testing migrations, execute SQL, identify unused databases, summarize usage, and coordinate branch handoffs between bots. ([Neon](https://neon.com/blog/neon-is-now-available-in-grok-bot "Neon is now available in Grok Bot - Neon"))

The interesting pattern is:

```text
                 AI Agent
                    │
                    ▼
                Neon MCP
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     Create       Branch      Execute
      DB          database      SQL
        │           │           │
        └───────────┼───────────┘
                    ↓
                PostgreSQL
```

And the branch-before-migration workflow is particularly useful:

```text
Production DB
      │
      ▼
Create branch
      │
      ▼
Agent tests migration
      │
      ▼
Run validation
      │
      ├── FAIL → discard
      │
      └── PASS → propose promotion
```

### Why it matters to you

This is **exactly the kind of architecture you should be experimenting with**.

Agents modifying databases is dangerous if they operate directly against production.

Database branching changes the equation:

> **Give the agent a disposable environment rather than trusting the agent not to make mistakes.**

That's a powerful architectural principle.

It also fits beautifully with your Postgres + Python + agent interests.

### Practical experiment

Build an agent workflow around a local or cloud Postgres database:

```text
User request
     ↓
Agent
     ↓
Create isolated DB branch
     ↓
Inspect schema
     ↓
Generate migration
     ↓
Execute
     ↓
Run tests
     ↓
Generate diff
     ↓
Human approval
     ↓
Production
```

That gives you hands-on experience with:

**MCP + database automation + branching + agent permissions + human-in-the-loop.**

That's an unusually high-value experiment.

**Source:** [Neon — Neon is now available in Grok Bot](https://neon.com/blog/neon-is-now-available-in-grok-bot)

## 5. Google Cloud's Managed Airflow now has an **AI agent + MCP control surface**

Google Cloud's Managed Service for Apache Airflow added an **Airflow Agent in the Google Cloud Console** and made its remote **MCP server generally available** in August. The agent can help diagnose failed tasks and DAG runs, identify performance bottlenecks and suggest or perform optimization work. ([Google Cloud Documentation](https://docs.cloud.google.com/composer/docs/release-notes "Managed Service for Apache Airflow release notes  |  Google Cloud Documentation"))

The September 2 release also added **OOM event logs** to Managed Airflow Gen 3 and improved resilience against transient Kubernetes pod connection failures. ([Google Cloud Documentation](https://docs.cloud.google.com/composer/docs/release-notes "Managed Service for Apache Airflow release notes  |  Google Cloud Documentation"))

The important architecture is:

```text
                Airflow
                   │
             Metrics / Logs
                   │
                   ▼
              MCP Server
                   │
                   ▼
              AI Agent
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
     Diagnose   Explain    Optimize
        │          │          │
        └──────────┼──────────┘
                   ↓
              Human / Policy
```

### Why it matters to you

This is a very practical example of where **Data Engineering + Agents** are converging.

Instead of an engineer manually doing:

```text
Airflow failure
 ↓
Open logs
 ↓
Find pod
 ↓
Inspect memory
 ↓
Check upstream task
 ↓
Search documentation
 ↓
Form hypothesis
```

an agent can increasingly perform that investigation across the operational surface.

But notice something important:

**the agent isn't the platform.**

Airflow still provides:

- execution
    
- scheduling
    
- logs
    
- state
    
- metadata
    
- operational APIs

The agent becomes an **intelligence layer over the platform**.

That's exactly how I'd think about your future Lakehouse Copilot.

### Practical experiment

Build an **Airflow diagnostic agent** locally.

Give it read-only access to:

- DAG metadata
    
- task logs
    
- execution durations
    
- retry counts
    
- resource metrics

Ask it:

> "Why did this DAG become slower over the last 7 days?"

Then force it to produce:

```text
Observation
Evidence
Hypothesis
Confidence
Recommended action
```

That turns a generic chatbot into an **engineering investigation system**.

**Source:** [Google Cloud — Managed Service for Apache Airflow release notes](https://docs.cloud.google.com/composer/docs/release-notes)
