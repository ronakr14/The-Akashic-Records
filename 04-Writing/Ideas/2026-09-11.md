I’d make this week a little more experimental. The strongest current signal is **AI infrastructure moving down into the data/system layer**, while DuckDB 2.0 is about to cross an important architectural boundary from embedded analytics toward client/server operation. ## 1. DuckDB 2.0: The Embedded Database Is Becoming a Data Service

**My top pick this week.**

DuckDB 2.0 entered feature freeze on September 2, with stable release projected for the second half of October. The 2.0 alpha already has Python/CLI clients, Quack moving toward 1.0, and extensions including DuckLake and Iceberg being tested against the new branch. ([DuckDB](https://www.duckdb.org/2026/09/02/try-duckdb-20-alpha "Try DuckDB v2.0-alpha – DuckDB"))

The architectural shift is the interesting part: **DuckDB is no longer confined to a single process.** Quack provides networked client/server access. ([DuckDB](https://duckdb.org/quack/ "Quack Remote Protocol – DuckDB"))

### Working title

**DuckDB 2.0: When an Embedded Database Stops Being Embedded**

### Outline

1. Why DuckDB succeeded as an embedded analytical database
    
2. The single-process model
    
3. Where that model starts breaking down
    
4. Quack
    
5. Client/server DuckDB
    
6. Remote query execution
    
7. Concurrency
    
8. DuckLake
    
9. DuckDB vs PostgreSQL
    
10. DuckDB vs SQLite
    
11. What this means for local-first architecture
    
12. Where DuckDB should _not_ be used
    

### Practical experiment

Build four configurations:

```text
SQLite
DuckDB embedded
DuckDB + Quack
PostgreSQL
```

Benchmark:

- concurrent reads
    
- concurrent writes
    
- analytical queries

That gives you actual numbers instead of another “DuckDB is fast” article.

# 2. Governance Is Becoming AI Context

This is probably the **best fit for your Context Engineer direction**.

Databricks published a particularly relevant piece on September 3 arguing that things traditionally treated as governance/compliance artifacts—**data contracts, classification tags, lineage, de-identification policies and model cards**—can become the semantic foundation for AI systems. ([OnlyLabs](https://www.onlylabs.fyi/signals/b67be605-3c74-4c13-8e3f-f73e7db156bb "Databricks (DBRX) Writing: Governance beyond security: knowledge, context & ontology on the lakehouse — onlylabs"))

That's a much more interesting framing than “metadata is important.”

### Working title

**Your Data Governance Artifacts Are Becoming AI Context**

### Core thesis

For years:

```text
Governance → Compliance
```

Increasingly:

```text
Governance
     ↓
Metadata + Semantics + Policies + Lineage
     ↓
AI Context
     ↓
Better Agents
```

### Outline

1. Governance was treated as overhead
    
2. Why agents change the economics
    
3. Data contracts as context
    
4. Lineage as context
    
5. Classification as context
    
6. Access policies as context
    
7. Ontologies
    
8. Agent grounding
    
9. Context freshness
    
10. Evaluating context quality
    
11. Reference architecture

```text

├── Schema

├── Lineage

```

# 3. Agent Skills vs RAG vs MCP: Three Different Ways to Give AI Context

This one is particularly interesting because **Agent Skills are becoming a concrete product pattern**, rather than just a theoretical idea.

Zoho's September 3 Catalyst 3.0 release combines Agent Skills, MCP and AI-assisted development, with its skills repository open-sourced.

At the same time, MCP is becoming the standardized tool/interface layer.

That gives you an opportunity to ask:

> **Are Skills, RAG and MCP solving the same problem—or fundamentally different problems?**

### Working title

**Agent Skills vs RAG vs MCP: Where Should AI Get Its Context?**

### Comparison

|Mechanism|Primary purpose|
|---|---|
|**RAG**|Retrieve information|
|**Skills**|Teach an agent how to perform a task|
|**MCP**|Expose tools/resources/actions|
|**Fine-tuning**|Change model behavior|

### Outline

1. The context problem
    
2. RAG
    
3. MCP
    
4. Agent Skills
    
5. Fine-tuning
    
6. Where they overlap
    
7. Where they don't
    
8. Combining all four
    
9. Architecture patterns
    
10. Decision framework
    

### Practical experiment

Give the same Data Engineering task to an agent under four conditions:

```text
A. Prompt only
B. Prompt + RAG
C. Prompt + Skill
D. Prompt + Skill + MCP
```

Measure:

- task completion
    
- hallucinations
    
- tool calls
    
- latency
    
- token usage
    
- correctness
    

That would make an unusually useful article.

**7–9 hours**

# 4. RAG Is Becoming a Data Engineering Problem

Databricks' current AI Search supports structured and semi-structured fields and filter-only queries, which is a good example of retrieval becoming a more general data-access problem rather than simply “vector search.” ([Databricks Documentation](https://docs.databricks.com/gcp/fr/release-notes/product/2026/september "September 2026 | Databricks on Google Cloud"))

There's also research such as **kRAIG**, which treats automated pipeline generation as a structured agent workflow with retrieval, validation and explicit intent handling. ([arXiv](https://arxiv.org/abs/2603.20311 "kRAIG: A Natural Language-Driven Agent for Automated DataOps Pipeline Generation"))

# 6. AI Inference Is Becoming a Data-Engineering Workload

There's a broader infrastructure trend worth watching: inference is becoming a major systems problem, with specialized chips and networking aimed specifically at low-latency AI workloads. This week's d-Matrix/NVIDIA announcement is a concrete example: d-Matrix plans to integrate its inference processors into NVIDIA systems using NVLink Fusion, targeting real-time AI services such as coding assistants and agents. ([Reuters](https://www.reuters.com/business/media-telecom/chip-startup-d-matrix-use-nvidia-chip-linking-tech-ai-servers-2026-09-10/ "Chip startup d-Matrix to use Nvidia chip-linking tech in AI servers"))
