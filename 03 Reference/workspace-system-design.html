Local-First AI Workspace

A practical system for high-velocity AI engineering

Designed for 1-in-10 experiment graduation, Claude Code as primary driver, and portable context across Ollama, Continue, Codex, and Windsurf — without tool lock-in or cognitive overload.

Primary Tool: Claude Code
Graduation Rate: ~10%
Context Format: Mixed (YAML + MD)
Automation: n8n (version-controlled)
01

Folder Architecture

The structure has six layers with deliberately different contracts. High-churn layers have minimal rules. Stable layers have enforced structure. The AI context layer cuts across all of them — it's not a folder, it's a protocol.

DIRECTORY TREE
~/workspace/
│
├── lab/                        # experiments — zero friction zone
│   ├── active/
│   │   ├── 2025-01-snowflake-cortex-bench/
│   │   ├── 2025-01-rag-chunking-test/
│   │   └── scratch/           # truly throwaway, not dated
│   └── stale/                  # auto-moved after 14 days no activity
│
├── projects/                   # promoted work — structured, AI-ready
│   ├── active/

│   │       ├── src/
│   │       ├── tests/
│   │       ├── docs/

│   └── paused/                 # structured but not active
│
├── systems/                    # long-lived, operational
│   ├── n8n/                    # version-controlled workflows
│   │   ├── workflows/
│   │   ├── credentials.example/
│   │   └── SYSTEMS.md         # operational runbook
│   ├── tools/                  # reusable scripts, CLIs, helpers
│   ├── infra/                  # docker-compose, configs
│   └── mcp-servers/            # custom MCP tools for Claude Code

│   └── obsidian-bridge/        # symlinks to good Obsidian notes
│

│   ├── completed/              # project + context snapshot preserved
│   └── abandoned/             # lab experiments that died
│
└── .workspace/                 # system-level AI context (broad awareness)

    ├── active-projects.md     # live status summary
    ├── tech-stack.md          # canonical stack reference
    └── conventions.md         # naming, patterns, rules

Layer Reasoning

lab/ experiments

Date-prefixed dirs only. No required structure. No .ctx/. A scratch/ subdir for things not worth naming. stale/ is auto-populated — not manually curated. The naming discipline is the only rule: YYYY-MM-topic.

The date prefix does two things: gives you chronological context when scanning, and exposes age to scripts for auto-stale logic.

projects/active/ structured

Every project here has a .ctx/ directory. This is the gate. You cannot promote to projects/ without creating the context pack. That friction is intentional — it forces the 1-in-10 decision to be deliberate.

paused/ preserves structure without the overhead of active maintenance.

systems/ operational

n8n lives here because it's already version-controlled — treat it the same as code. mcp-servers/ matters: custom MCP tools you build for Claude Code belong here, not scattered in projects. Centralizing them means every project can use them.

knowledge/ curated

This is not your Obsidian vault. It's a curated extraction layer. Only content that earns its place gets here — ADRs, patterns that recurred in 2+ projects, external references you actually cite. The obsidian-bridge/ is symlinks, not copies.

⚠ On Obsidian Integration
Since your vault is mostly fleeting notes, don't try to structure it. Instead, build a promotion path: when a note graduates (you've referenced it twice or it has real substance), symlink it into knowledge/ and leave the original in Obsidian. Don't sync bidirectionally — that creates drift.
02

Context Protocol (Portable Context Pack)

The .ctx/ directory is a standardized AI context pack that lives inside every structured project. Its job: any AI tool can read these files and reconstruct enough understanding to be useful — without requiring conversational warm-up.

Design Principle
Context files are written for AI consumption first, human convenience second. Dense, explicit, no assumed knowledge. Write as if the reader has never seen your codebase. 
CONTEXT PACK STRUCTURE
project/
└── .ctx/
    ├── overview.md         # What + Why. Primary AI entry point.
    ├── state.md            # Current status, blocking issues, next step.
    ├── decisions.md        # Architecture decisions with reasoning.
    ├── tasks.md            # Scoped task list. Not a backlog.
    ├── constraints.md      # Hard limits: tech, perf, org, security.
    └── index.yaml          # Machine-readable metadata + file manifest.

overview.md — The AI Entry Point

.ctx/overview.md Required · Stable 
# cortex-rag-pipeline

## Purpose
Production RAG pipeline running natively in Snowflake using Cortex Search
and Cortex Complete. Replaces a Python-based LangChain prototype that had
unacceptable latency and vendor lock-in for embedding model swaps.

## What it does
- Ingests documents from an S3-staged Snowflake external stage
- Chunks and embeds via EMBED_TEXT_1024 (Snowflake-managed)
- Stores vectors in a dedicated VECTOR column in the DOCUMENTS table
- Serves queries through Cortex Search with hybrid retrieval fallback
- Returns augmented responses via COMPLETE('mistral-large', ...)

## Stack
- Snowflake Cortex (Search + Complete + Embed)
- Snowpark Python for ingestion pipeline
- Dynamic Tables for incremental refresh
- dbt for transformation layer (staging → mart)

## Non-goals
- No external embedding APIs (Snowflake-managed only)
- No streaming response (batch only for now)
- Not handling multi-modal content

.ctx/state.md Required · Evolving

decisions.md — Architecture Decisions

.ctx/decisions.md Required · Append-only 
## ADR-001 — Use Snowflake-managed embeddings only
**Date:** 2025-01-08
**Status:** Accepted
**Decision:** Use EMBED_TEXT_1024 exclusively. No external API calls.
**Reasoning:** Security review requires all data to stay within Snowflake
boundary. External embedding APIs would require egress approval.
Tradeoff: we lose model choice flexibility. Accepted — model swap
can be revisited when Cortex expands embedding model catalog.

---

## ADR-002 — Dynamic Tables over Streams+Tasks for incremental refresh
**Date:** 2025-01-10
**Status:** Accepted
**Decision:** Use Dynamic Tables with 1-minute lag target for document sync.
**Reasoning:** Streams+Tasks would require manual orchestration of
multi-step DAG. Dynamic Tables handle dependency resolution automatically.
Tradeoff: less control over execution order. Acceptable for current scale.
**Revisit if:** document volume exceeds 1M rows or lag requirements tighten.

constraints.md — Hard Limits

.ctx/constraints.md Required · Rarely changes 
## Hard Constraints

### Security
- No data egress outside Snowflake boundary
- All credentials via Snowflake secrets — no .env files in repo
- PII columns (user_email, user_id) masked via Dynamic Data Masking
  for all non-SYSADMIN roles

### Performance
- Ingestion pipeline: <5 min for 1000 documents end-to-end
- Query latency: p95 < 3s for single-turn RAG response

### Technology
- Snowflake Enterprise (not Business Critical) — some features unavailable
- Python 3.11 (Snowpark constraint) — no 3.12+ features
- dbt Core only — no dbt Cloud

### Org
- No external vendor dependencies without security review
- Breaking schema changes require 1-week notice to downstream teams

What NOT to Include in .ctx/

  • Full file dumps or long code pastes — link to files, don't embed them
  • Meeting notes, chat logs, raw brainstorms — these belong in Obsidian
  • Every possible option considered — only decisions made, with rationale
  • Version history or changelogs — that's what git is for
  • Aspirational future state — only what's true now and what's next
  • Context from other projects — each .ctx/ is self-contained

How Context Evolves

FileUpdate TriggerWho Updates
overview.mdScope changes, non-goals discoveredYou, rarely
state.mdEvery work session start/endYou or ask AI to update it
decisions.mdAny architectural decision madeYou, append-only
tasks.mdTask completed or scope shiftsYou or ask AI to update it
constraints.mdNew hard limit discoveredYou
index.yamlStatus/phase changes, new relationsPromotion script
Practical Habit
End every significant work session with: "Update state.md to reflect what changed today and what's blocked." — directed at whatever AI you're using. Takes 30 seconds and keeps context fresh with zero overhead.
03

AI Interoperability Strategy

The core insight: you have one context format, not five tool-specific formats. Each tool reads .ctx/ differently, but the files are identical. This is what portability actually means.

Tool-by-Tool Injection Strategy

Claude Code — Primary Driver

CLAUDE.md Project root · Auto-loaded

Claude Code auto-reads CLAUDE.md from project root and any parent dirs. This is your primary injection mechanism. Keep it lean — it's a pointer, not a dump.

# CLAUDE.md (project root)

## Context Pack
Read .ctx/overview.md, .ctx/state.md, .ctx/constraints.md before
responding to any request. Load decisions.md if the task involves
architecture or schema changes. Load tasks.md for task execution.

## Working Rules
- All data must stay within Snowflake boundary (see constraints.md)
- Do not suggest external embedding APIs
- When updating state.md, keep it under 40 lines
- Prefer Dynamic Tables over Streams+Tasks unless explicitly asked

## Quick Stack Reference
Snowflake Cortex · Snowpark Python 3.11 · dbt Core · Dynamic Tables

Also create a workspace-level CLAUDE.md in ~/workspace/ that points to .workspace/index.md for broad awareness.

Continue (VS Code) — In-Editor Assistant

.continuerc.json Project root · Custom docs

Continue supports custom context providers and @docs. Wire it to read your .ctx/ files as custom documentation:

{
  "contextProviders": [
    {
      "name": "file",
      "params": {
        "defaultFile": ".ctx/state.md"
      }
    }
  ],
  "docs": [
    {
      "title": "Project Overview",
      "startUrl": ".ctx/overview.md"
    }
  ],
  "systemMessage": "You are working in the cortex-rag-pipeline project.
    Always read .ctx/state.md before answering questions about current
    status. Hard constraints are in .ctx/constraints.md."
}

In practice: use @file .ctx/state.md in the Continue chat for quick state injection. Don't paste the whole context pack — Continue is for in-file edits, not architecture sessions.

Ollama — Local Models

ctx-inject.sh systems/tools/ · Context injector

Ollama has no native project-awareness. Build a lightweight shell tool that assembles context into a prompt prefix:

#!/bin/bash
# systems/tools/ctx-inject.sh
# Usage: ctx-inject.sh [project-path] | ollama run llama3.2

PROJECT=${1:-$(pwd)}
CTX="$PROJECT/.ctx"

if [ ! -d "$CTX" ]; then
  echo "No .ctx found at $PROJECT" >&2
  exit 1
fi

echo "=== PROJECT CONTEXT ==="
cat "$CTX/overview.md"
echo ""
echo "=== CURRENT STATE ==="
cat "$CTX/state.md"
echo ""
echo "=== CONSTRAINTS ==="
cat "$CTX/constraints.md"
echo "=== END CONTEXT === Answer the following:"

Pipe output into your Ollama call. Keep total context under 2000 tokens for smaller local models — use inject_priority from index.yaml to pick which files to include.

Windsurf — Cascade Context

Windsurf Rules .windsurfrules · Workspace level

Windsurf's Cascade reads .windsurfrules in the project root. Wire it the same way as CLAUDE.md — point to .ctx/:

# .windsurfrules
Always read .ctx/overview.md and .ctx/constraints.md before
suggesting code changes. Hard constraints take priority over
any optimization. When making architectural suggestions,
check .ctx/decisions.md first to avoid re-litigating closed decisions.

Codex

Codex (OpenAI) benefits from the same AGENTS.md / system prompt pattern. If using via API, prepend the assembled context pack output. If using CLI, a .codex-context file in project root works as a system-level inject.

Depth vs. Breadth Balancing

ScenarioWhat to InjectTool
Deep work on one project Full .ctx/ (all 5 files) Claude Code
Quick edit / in-file fix state.md + constraints only Continue / Windsurf
Cross-project question .workspace/active-projects.md Claude Code at workspace root
Local model exploration overview.md + state.md only Ollama via ctx-inject.sh
New session, lost context index.yaml → pick files by inject_priority Any tool
⚠ Context Window Discipline
The most common failure: injecting too much context and degrading response quality. The inject_priority field in index.yaml exists exactly for this. For smaller models (Ollama, 7B-13B), never exceed overview.md + state.md. For Claude, the full pack is fine but still not necessary for simple tasks.

Promotion & Lifecycle Rules

Experiment → Stale (Auto, 14 days)

Any experiment with no file changes in 14 days moves to lab/stale/. No decision needed. Implement with a cron job or n8n workflow — this should be automatic, not a weekly chore.

BASH
find ~/workspace/lab/active -maxdepth 1 -mindepth 1 -type d \
  -not -newer $(date -d "14 days ago" +%Y%m%d) \
  -exec mv {} ~/workspace/lab/stale/ \;

Experiment → Project (Manual, Deliberate)

Promotion is not automatic. These criteria must be met — all three:

  • Signal: The experiment has produced something you want to use again or build on, not just understand
  • Boundary: You can articulate what it does AND what it explicitly doesn't do (non-goals exist)
  • Investment: You're willing to spend 20 minutes creating the full .ctx/ pack right now

If any of those three fails — it's not ready. Leave it in lab/active/ or let it go stale.

Promotion Script
Create a promote.sh in systems/tools/ that scaffolds the .ctx/ directory with templated files and pre-fills index.yaml from the lab dir metadata. Reducing friction on the one moment that matters makes the 1-in-10 rate healthier.

Project → Paused

  • No active work for 30 days AND you have no near-term plan to resume
  • Before pausing: update state.md with a resume note — specifically what the next action is
  • Structure stays intact. .ctx/ stays current. Move, don't modify.

→ Archive: Completed

  • Take a final snapshot: run a script that copies the .ctx/ + docs/ to archive/completed/project-name/
  • Extract any reusable ADRs into knowledge/decisions/ before archiving
  • Update .workspace/active-projects.md to remove it

→ Archive: Abandoned (Stale → Dead)

  • Stale for 60+ days with no promotion intent
  • Move to archive/abandoned/ — compressed if large, otherwise as-is
  • No documentation required. Just move it.

Clutter Prevention Rules

Agent / Workflow Layer (Lightweight)

No LangChain. No orchestration framework. The insight: roles are just system prompts + context file subsets. You already have structured context — the "agent" is just how you frame the request against it.

Three Roles, Three Context Subsets

Planner Role Claude Code · Session start

Context injected: overview.md + state.md + tasks.md

Prompt pattern:

"You are a planner. Read the provided context.
Do not write code. Identify the single most
important thing to work on next given current
state and blockers. Explain your reasoning in
under 100 words."

Use at session start when you're not sure where to pick up.

Executor Role Claude Code / Continue · Task work

Context injected: constraints.md + relevant source files

Prompt pattern:

"You are an executor. The task is: [specific task].
Hard constraints are in constraints.md — these
are non-negotiable. Generate the implementation.
Flag anything that might violate a constraint
before proceeding."

Constraints-only injection keeps the context window tight for code generation.

Reviewer Role Claude Code · Before commit

Context injected: decisions.md + constraints.md + diff/changed files

Prompt pattern:

"You are a reviewer. Check this implementation
against: (1) hard constraints, (2) existing ADRs,
(3) correctness. Do NOT suggest improvements
outside scope. Flag violations only."

The "no out-of-scope suggestions" instruction prevents reviewer bloat.

Scribe Role Session end · Context maintenance

Context injected: state.md (current) + conversation summary

Prompt pattern:

"You are a scribe. Update state.md to reflect:
what was accomplished, what's now blocked,
and what the immediate next action is.
Keep it under 40 lines. Preserve format."

Run at session end. Keeps context fresh for the next session automatically.

Implementation: Prompt Templates as Files

Store these as markdown files in systems/tools/prompts/. Use them by reading + appending context, not by building a framework.

DIRECTORY
systems/tools/prompts/
├── planner.md
├── executor.md
├── reviewer.md
└── scribe.md

For Claude Code: add a single line to CLAUDE.md that says where to find them. For Ollama: pipe them into ctx-inject.sh. No framework needed — just files.

n8n as Lightweight Orchestrator

For anything repetitive (daily state summaries, auto-stale moves, context freshness checks), use n8n. Not as an agent framework — as a cron job with HTTP calls. A simple workflow that reads state.md age and flags projects that haven't been updated in 7 days costs 30 minutes to build and runs forever.

Graph Integration

Graph is high value for you specifically because you have a cross-cutting systems layer (n8n, tools) that multiple projects depend on, and a knowledge base that should be linked to decisions. The risk: you build a beautiful graph that's never consulted.

What to Link (and What Not To)

Link TypeValueInclude?
project → system dependencyHigh — shows blast radius of system changesYes
project → ADRHigh — traceabilityYes
experiment → knowledge noteMedium — shows what informed the experimentYes, sparingly
experiment → experimentLow — usually noiseNo
project → every tool usedVery low — becomes a dependency graph, not a knowledge graphNo

Encoding Links in index.yaml

The related_projects and related_systems fields in index.yaml are your graph edges. They're machine-readable, which means Graphify (or any tool) can consume them directly without a separate graph database.

INDEX.YAML — RELATIONSHIP FIELDS
related_projects:
  - projects/active/snowflake-governance-layer  # shares DDM patterns
related_systems:
  - systems/n8n                                 # triggers ingestion
  - systems/tools/ctx-inject.sh                 # used for local model eval
knowledge_refs:
  - knowledge/decisions/ADR-001-embeddings.md
  - knowledge/patterns/snowflake-dynamic-tables.md

How Graph Enhances AI Context

Add a workspace graph summary to .workspace/index.md — a plain-text adjacency description. When asking Claude Code a cross-project question, inject this file. It gives broad awareness without requiring the AI to traverse actual graph files.

.WORKSPACE/INDEX.MD — GRAPH SUMMARY SECTION
## Project Relationships

cortex-rag-pipeline
  → depends on: systems/n8n (ingestion trigger)
  → shares patterns with: snowflake-governance-layer (DDM)
  → informed by: ADR-001 (embedding model constraint)

snowflake-governance-layer
  → depends on: systems/tools/ddm-validator.py
  → no active project dependencies
⚠ Graph Noise Anti-Pattern
Don't link everything to Obsidian notes — your vault is mostly fleeting notes and most of them will be stale or irrelevant. Only link notes that have been curated into knowledge/. Graph noise (many low-value links) degrades AI context quality faster than missing links do.
07

Anti-Patterns

These are specific failure modes for your working style — not generic productivity warnings.

Where This System Will Break

Anti-Pattern 1: Context Staleness Spiral High Risk for You

How it happens: You promote an experiment, create a great .ctx/ pack, then do two weeks of work without updating state.md. Now the context pack describes a project from two weeks ago. AI suggestions start subtly degrading because they're based on an outdated problem statement.

Fix: The Scribe role prompt at session end. Make it a muscle memory habit, not an optional step.

Anti-Pattern 2: Lab as Purgatory High Risk for You

How it happens: With a 1-in-10 graduation rate, you'll have a lot of good-but-not-promoted experiments. You'll resist archiving them because "I might come back to this." Over time, lab/active/ fills with 40 dirs and becomes cognitively heavy even though 90% are dead.

Fix: The 14-day auto-stale script is not optional. It's the only thing that keeps this honest. The archive is not deletion — it's just out of sight.

Anti-Pattern 3: Obsidian Gravity Medium Risk for You

How it happens: You start capturing project decisions in Obsidian because you're already there. Then ADRs exist in two places. Then the .ctx/decisions.md is always outdated relative to Obsidian. Then neither is trustworthy.

Fix: Obsidian is for thinking. .ctx/ is for AI context. They don't compete if you're strict about it. Never write an ADR in Obsidian — write it in decisions.md, then optionally link it from Obsidian.

Anti-Pattern 4: Context Pack Perfectionism Medium Risk

How it happens: You spend 90 minutes crafting a perfect .ctx/ at promotion time instead of 20 minutes on a good-enough one. This raises the perceived cost of promotion, so you promote less. The 1-in-10 rate drops to 1-in-30 and good experiments die.

Fix: Use the promotion script with templated files. A 60% complete state.md on day 1 is infinitely better than a perfect one you never write. The Scribe role fills the gaps over time.

Anti-Pattern 5: Tool-Specific Context Drift Medium Risk

How it happens: You build a nice CLAUDE.md and then start adding Windsurf-specific context to .windsurfrules that contradicts it. Now you have two sources of truth and they disagree about constraints.

Fix: Tool config files (CLAUDE.md, .windsurfrules, .continuerc.json) are pointers only — they reference .ctx/ files, they never contain substantive context themselves. If you want to update a constraint, update constraints.md, not the tool config.

Anti-Pattern 6: n8n Sprawl Bleeding Into This System Low-Medium Risk

How it happens: Because n8n is already in systems/ and version-controlled, you start using it for workspace automation (auto-stale, context checks) AND for project-level pipelines. Now n8n has two different jobs and systems/n8n/ is a mess of unrelated workflows.

Fix: Separate n8n workflows by concern with subdirectories: systems/n8n/workspace/ for automation of this system, systems/n8n/pipelines/ for data work. The SYSTEMS.md runbook documents which is which.

Assumptions I'm Challenging

  • "Flexibility over rigid structure" — You need rigid interfaces (context pack format, promotion gate, stale rules) to support flexible internals. The flexibility you want is in what you build, not in how the system is organized.
  • "Obsidian as knowledge base" — With mostly fleeting notes, Obsidian is a thinking tool, not a knowledge base. Treating it as the latter will make both functions worse. The knowledge/ dir is your knowledge base.
  • "More AI tools = more capability" — Five tools with inconsistent context is worse than two tools with excellent context. The interop strategy only works if you maintain the .ctx/ files. Every tool you add increases that maintenance surface.
Final Note on Tradeoffs
This system has one real weakness: it requires consistent investment in context maintenance. If you do it, AI quality compounds over the life of a project. If you don't, it degrades faster than having no system at all — because you'll trust stale context that's wrong rather than having no context and asking first. The Scribe habit at session end is the load-bearing habit. Everything else is structure.
