These questions target your AWS + ADF multi-cloud setup. Interviewers want to know you made deliberate infrastructure decisions, not just used what was available.

Hard
Architecture
You ran AWS Glue and Azure Data Factory in the same pipeline. How did you handle orchestration, monitoring, and failure recovery across two clouds?
Sample answer
The split was by data source ownership — the healthcare client's core EHR data lived in Azure, so ADF was the natural extraction tool there. Our transformation and loading infrastructure was on AWS, so Glue ran the heavy transformation jobs before landing data into Snowflake.

Orchestration sat in Airflow on AWS. ADF pipelines were triggered via the Azure REST API from Airflow tasks — we'd fire the ADF run, poll for completion using an ADF sensor operator, and gate the downstream Glue job on a successful ADF run status. Failures on either side fired the same CloudWatch-based alerting pipeline, so oncall didn't need to context-switch between Azure Monitor and CloudWatch depending on where the failure occurred.

The main operational headache was credential management across clouds. We used AWS Secrets Manager as the single source of truth for all credentials — including the Azure service principal used to call the ADF API. That way rotation happened in one place and both the Glue jobs and the Airflow ADF trigger used the same secrets retrieval pattern.

Failure recovery across the boundary was the trickiest part. If ADF succeeded but the Glue transformation failed, we needed to re-run only the Glue side without re-extracting from Azure — which would be expensive and potentially introduce duplicate records. We solved this by writing ADF output to an S3 staging zone before Glue picked it up. On Glue failure, the re-run reads from S3 staging, not from Azure. The staging files were retained for 48 hours and then expired via S3 lifecycle policy.
Coaching note: The S3 staging zone as a cross-cloud idempotency buffer is the most architecturally interesting detail — lead with it if the interviewer probes on multi-cloud reliability.

Walk me through the full architecture of your RAG-to-SQL system.
Sample answer
The system sat on top of a multi-database healthcare warehouse — PostgreSQL, SQL Server, and Snowflake — each with its own schema conventions, so the first challenge was building a unified metadata layer.

I started by extracting schema metadata: table names, column names, data types, foreign key relationships, and business glossary terms. I chunked these at the table level — one document per table containing its column definitions, sample values, and join patterns. These were embedded using OpenAI's text-embedding-ada-002 and stored in PgVector.

At query time, the user's natural language question gets embedded and we do a dense similarity search to retrieve the top-5 most relevant table contexts. I found that pure dense retrieval struggled with exact column name matching, so I added a keyword filter layer on top — effectively a hybrid retrieval pattern.

The retrieved schema context gets injected into a prompt that instructs the LLM to generate SQL constrained to only the tables provided. Before execution, the SQL goes through a validation layer: we parse it with sqlparse to verify table and column names actually exist in the schema, and we check for any cross-database joins that would fail at runtime.

The tricky part was multi-domain queries — a question about pharmacy sales reconciliation might need to join across Snowflake and PostgreSQL. We handled that by routing those queries through a federated query layer using Snowflake's external tables to mirror the PG data, so everything could be executed from a single endpoint.

The 60% reduction in analyst query effort was measured by tracking ticket volume in our internal request queue before and after rollout, over a 6-week period. It was directional, not a controlled experiment — but the trend was consistent.
Coaching note: Lead with the hardest architectural decision you made — in this case, hybrid retrieval over pure dense search. That signals you evaluated alternatives, not just implemented the first thing.
